What actually labels a history row?

The rows above show a song on one line and an artist underneath. That data does not exist today. GenerateResult carries the style prompt, lyrics, cover-art prompt, genres, and the invented band/title/album ideas — never the real ones. The prompt forbids them twice: “NEVER mention real artist, band, or song names in any output.” The only place the real song lives is the reference string you typed. Three ways to label a row:

L1  The reference, verbatim

One line, exactly as typed. Nothing to get wrong and nothing new to build — but rows are ragged, since people type “Metallica, Enter Sandman”, “Enter Sandman by Metallica” and “enter sandman” interchangeably.

  • Metallica, Enter Sandman
    thrash metal · heavy metal    2h
  • Enter Sandman by Metallica
    thrash metal    Yest.
  • blue monday new order
    synth-pop · post-punk    Tue

L2  Split on the comma

Client-side guess: text before the comma is the artist, after it the song. Free, and right for the format the placeholder suggests — wrong the moment someone writes “by”, reverses the order, or omits one. No way to tell a bad split from a good one.

  • Enter Sandman
    Metallica    2h
  • —
    Enter Sandman by Metallica    Yest.
  • —
    blue monday new order    Tue

Two of three misparsed. Nothing detects it.

L3 · recommended  Ask the model

Turn 1 already researches the song, so it knows. Two extra fields — the real artist and the real title — returned as metadata about the reference, never as prompt content. Rows become uniform and sortable regardless of how the reference was typed. Falls back to L1 verbatim if the fields come back empty.

  • Enter Sandman
    Metallica · thrash metal    2h
  • Enter Sandman
    Metallica · thrash metal    Yest.
  • Blue Monday
    New Order · synth-pop    Tue

All three typed differently. Same row shape.

catch  What L3 costs

It needs a deliberate hole in a rule that currently has none. The carve-out has to be narrow and explicit, or the model starts reading it as permission to put real names in the style prompt — which is the thing the rule exists to stop.

// added to turn 1
3. referenceArtist, referenceTitle — the REAL artist and title of the
   reference song you researched. These two fields are the ONLY
   place a real name may ever appear: they label the run in a list
   and are never pasted into Suno. The rule still holds absolutely
   for stylePrompt, lyrics, titles, albums, bands and the cover-art
   prompt. Leave them empty if unsure.

Costs no extra tool call and no extra turn — two more keys in a JSON object turn 1 already returns.

also  Where the refine box says it

Whichever of 1–3 you pick, the refine field is the place the overwrite actually happens. A quiet line under it carries the rule, so nobody has to open history to learn it.

Refine the lyrics — e.g. “darker chorus”

Refining rewrites these lyrics and updates this run’s saved copy. The previous wording is not kept.

Both questions

Opening a saved run

Everything the run produced comes back — not a summary. All three band, title and album ideas (not just the one you happened to copy), the genre chips, the full lyrics, the style prompt with its character count, the cover-art prompt, and the cover image itself if one was generated. Same cards as a live run, minus everything that would change it: no refine field, no editable boxes, no “Generate cover art” button. Copy buttons stay — that is the whole point of keeping the run. The only way forward is a fresh generation, which starts a new entry rather than continuing this one.

It is enough content that a modal gets tall. Shown here as a sheet to match how the app already opens things, but it could equally be a full page — worth deciding along with placement A/B/C.

Before building

Things the mockups can’t decide

QuestionWhy it matters
Where storedServer-side (SQLite, survives devices, needs a table + endpoints) or browser-local (localStorage, zero backend, lost on another device or a cleared cache).
How muchKeep the last N runs, or everything with a delete button. Lyrics are a few KB each, so either is cheap — this is about clutter, not storage.
When it savesOn the first card landing (a failed run leaves a stub) or only on a completed run (a run that died mid-way is lost).
Cover artThe image is ephemeral today. The mock above assumes it is kept with the run — that means storing PNGs, not just text, and is the one part of “all the data” that costs real disk. Say if the prompt alone is enough.
Run detailsThe mock keeps the reference, timestamp, duration, the refine instructions used, and a foldaway research trail. Any of that not worth storing?
Other modesGenre → Fanart and Album Cover also generate. Same history, separate history, or Suno runs only for now.
Hand editsLyrics and the cover-art prompt are editable in place today. Does typing in them update the saved copy, or only a refine?
